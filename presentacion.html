Contexto y Fundamentos

El cambio es inevitable; el riesgo no

Expositora: Heidy
⚠️ La fragilidad del código en producción

El software cambia durante toda su vida útil. Cada modificación manual sobre código que ya funciona puede introducir errores colaterales imprevistos (regresiones).

Un pequeño cambio para una nueva regla de negocio puede romper supuestos de módulos distantes que daban por seguro el comportamiento original.

🛡️ El objetivo del Principio OCP

El OCP busca que los sistemas de software crezcan incorporando nuevo código en lugar de reescribir y alterar el código preexistente y probado.

Definición Canónica

Abierto para extensión. Cerrado para modificación.

Expositora: Heidy

"Las entidades de software (clases, módulos, funciones) deben estar abiertas para su extensión, pero cerradas para su modificación."

— Robert C. Martin (Uncle Bob)
ABIERTO
Para la Extensión

Significa que el comportamiento de un módulo puede ser ampliado. Cuando los requerimientos del negocio cambian, podemos hacer que el módulo se comporte de maneras nuevas y diferentes.

CERRADO
Para la Modificación

Significa que nadie tiene permiso para alterar el código fuente ya existente y probado. Ese código permanece intacto y blindado contra posibles regresiones y efectos no deseados.

Evolución Teórica

Dos interpretaciones del mismo principio

Expositora: Heidy
Criterio 1. Enfoque de Bertrand Meyer (1988) 2. Enfoque Polimórfico de Robert Martin (1996)
Mecanismo principal Herencia clásica de clases concretas Interfaces y Clases Abstractas (Polimorfismo)
Cómo se extiende Creando una subclase que hereda variables y métodos Implementando el contrato de la interfaz
Acoplamiento Fuerte acoplamiento con la clase base (herencia rígida) Débil acoplamiento con abstracciones estables
Estado en la industria Considerado restrictivo o frágil en sistemas grandes Estándar adoptado universalmente en arquitectura limpia
💡
Regla moderna: Preferir composición y contratos abstractos antes que herencia profunda para evitar la fragilidad de las clases base.
Anti-patrón / Código Malo

El Problema: El 'switch' que se reabre siempre

Expositor: Santiago 
public class GraphicEditor {

    public void drawShape(Shape s) {
        switch (s.getType()) {
            case "CIRCLE" -> drawCircle(s);
            case "SQUARE" -> drawSquare(s);
            
            // ❌ NUEVA FIGURA: ¡Obligados a modificar aquí!
            case "TRIANGLE" -> drawTriangle(s);
        }
    }

    private void drawCircle(Shape s) { ... }
    private void drawSquare(Shape s) { ... }
    private void drawTriangle(Shape s) { ... }
}
❌ ¿Por qué viola el OCP?
  • No está cerrado a modificación: Cada vez que el negocio inventa una figura nueva, debemos abrir y alterar GraphicEditor.
  • Riesgo de regresión: Tocar este método puede accidentalmente romper el dibujado del círculo o del cuadrado.
  • Re-testeo masivo: Obliga a re-compilar y volver a certificar la clase completa en cada sprint.
Solución con OCP

La Solución: Depender de una Abstracción

Expositor: Santiago 
// 1. Contrato abstracto estable
public interface Shape {
    void draw();
}

// 2. Clase cliente CERRADA a modificación
public class GraphicEditor {
    public void drawShape(Shape s) {
        s.draw(); // ¡Polimorfismo dinámico puro!
    }
}

// 3. Extensión libre sin tocar GraphicEditor
public class Triangle implements Shape {
    public void draw() { System.out.println("Dibujando triángulo"); }
}
«interface»
Shape
+ draw(): void
Circle
+ draw()
Triangle
+ draw()
✔ Para añadir un Pentágono solo creas una clase nueva. GraphicEditor ni se entera.
Ingeniería de Software

Tres mecanismos para cerrar un módulo

Expositor: Santiago
1
Abstracciones Estables

Diseñar interfaces o clases abstractas que definen el contrato funcional invariable. Lo que es común no cambia; lo que varía se abstrae.

2
Polimorfismo Dinámico

Delegar la decisión de ejecución al despacho dinámico en tiempo de ejecución. La clase invocadora sólo sabe qué mensaje enviar, no cómo se resuelve.

3
Composición e Inyección

Inyectar el comportamiento en el constructor o método en lugar de crear instancias rígidas con new dentro de la clase de negocio.

Protected Variation (Larman, 2001): "Identifica los puntos de variación previstos y crea una interfaz estable alrededor de ellos."
Caso Real de Negocio

Caso Práctico: Descuentos en Tienda

Expositor: Santiago
❌ SIN OCP: Código Vulnerable
public class CalculadoraPrecios {
    public double calcular(double precio, String promo) {
        if (promo.equals("ESTUDIANTE")) {
            return precio * 0.90;
        } else if (promo.equals("BLACK_FRIDAY")) {
            return precio * 0.70;
        } else if (promo.equals("NAVIDAD")) {
            return precio * 0.80; // Modificando!
        }
        return precio;
    }
}
✔ CON OCP: Escalable y Limpio
public interface Descuento {
    double aplicar(double base);
}

public class DescuentoBlackFriday implements Descuento {
    public double aplicar(double base) { return base * 0.70; }
}

// El procesador jamás se reabre ni se altera
public class CalculadoraPrecios {
    public double calcular(double base, Descuento desc) {
        return desc.aplicar(base);
    }
}
Adopción Industrial

OCP en el Ecosistema Java del Mundo Real

Expositor: Santiago
🗄️ JDBC (Java Database Connectivity)

La librería estándar define las interfaces Connection, Statement y ResultSet.

Extensión sin modificación: MySQL, PostgreSQL u Oracle crean su propio driver .jar. Java nunca necesitó ser recompilado para soportar un nuevo motor de base de datos.

🌐 Servlet API & Spring Framework

Los servidores web (Tomcat, Jetty) dialogan exclusivamente con la interfaz abstracta HttpServlet.

Extensión sin modificación: Nosotros escribimos nuestros controladores y lógica de negocio implementando esa interfaz sin tener que alterar el código del servidor Tomcat.

Balance Técnico

Comparativa: Antes vs. Después de OCP

Expositor: Johan
Criterio Sin OCP (Código Acoplado) Con OCP (Código Polimórfico)
Incorporación de cambios Editar y reabrir clases existentes Crear una nueva clase que implementa la interfaz
Riesgo de regresión Alto (puede romper funcionalidades ya operativas) Nulo (el código viejo no se toca)
Pruebas Unitarias Obliga a re-ejecutar pruebas en todo el módulo Solo se prueba la nueva clase creada
Legibilidad Condicionales (if/switch) gigantescos Clases pequeñas con propósito explícito
Costo Inicial Rápido al inicio (programar un if) Mayor esfuerzo inicial de modelado y abstracción
Patrones de Diseño (GoF)

Patrones de Diseño que materializan OCP

Expositor: Johan
STRATEGY
Patrón Estrategia

Encapsula algoritmos intercambiables bajo una misma interfaz. Permite cambiar el comportamiento en tiempo de ejecución (ej. métodos de pago, cálculo de rutas, compresión).

DECORATOR
Patrón Decorador

Añade responsabilidades y comportamientos adicionales a un objeto dinámicamente envolviéndolo, sin tener que alterar la clase original ni crear subclases excesivas.

TEMPLATE METHOD
Método Plantilla

Define el esqueleto invariable de un algoritmo en una clase base cerrada, y delega los pasos variables específicos a subclases que extienden el proceso.

Pragmatismo & Buenas Prácticas

Cerrar todo es imposible — y contraproducente

Expositor: Johan
🟢 Variación Real y Frecuente

Se justifica aplicar OCP cuando el negocio cambia repetidamente en ese punto específico (ej. promociones, pasarelas de pago, exportación a formatos).

✔ Protege la inversión y reduce costos de mantenimiento.
🔴 Variación Hipotética (Sobreingeniería)

Crear interfaces y fábricas para módulos que nunca van a cambiar añade complejidad accidental y código difícil de navegar.

❌ Viola el principio YAGNI (You Aren't Gonna Need It).
Regla del Pulgar de Robert Martin: "La primera vez que escribes código, hazlo simple. Solo cuando el cambio ocurra una segunda o tercera vez, refactoriza aplicando OCP."
Arquitectura Limpia

OCP funciona dentro del sistema SOLID

Expositor: Johan
S
Single Responsibility
O
Open / Closed
L
Liskov Substitution
I
Interface Segregation
D
Dependency Inversion
🔗 La 'D' respalda directamente a la 'O'

El Principio de Inversión de Dependencias (DIP) es el habilitador del OCP: establece que los módulos de alto nivel no deben depender de implementaciones concretas, sino de abstracciones. Sin DIP, no se puede cerrar una clase.

🔄 La 'L' garantiza la sustitución segura

El Principio de Sustitución de Liskov (LSP) asegura que cualquier nueva subclase o implementación que añadamos respete el contrato de la interfaz sin alterar el comportamiento esperado por el cliente.

Conclusiones

Diseñar para cambiar, sin diseñar de más

Expositor: Johan
1. Estabilidad mediante Contratos

Proteger el código estable existente aislándolo detrás de interfaces bien definidas, garantizando cero impacto sobre funcionalidades en producción.

2. Aplicación con Evidencia

Aplicar OCP en puntos de variación frecuentes y demostrados, evitando la sobreingeniería y el exceso prematuro de capas.

3. Polimorfismo vs Herencia

Preferir siempre la abstracción polimórfica (Martin) antes que la herencia estricta de implementación (Meyer) para mantener bajo acoplamiento.

4. Demostración en Código

El repositorio en GitHub incluye ejemplos funcionales en Java con pruebas unitarias demostrando la refactorización paso a paso.
